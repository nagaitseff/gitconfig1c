# Git для больших репозиториев 1С ERP

Дата проверки документации: 24.10.2026. Версия комплекта: 1.0.

Готовый профиль для текстовой выгрузки конфигурации: много BSL/XML/EDT-файлов, крупные обновления ERP, длительная история и несколько рабочих веток. Это выбранная отправная точка, а не обещание максимальной скорости на любом компьютере.

Основной файл рассчитан на native Git 2.40+. Для нового рабочего места разумно использовать актуальный поддерживаемый выпуск Git; дополнительные настройки в modern-профиле требуют 2.56+. Версия Git внутри IDE может отличаться от версии в терминале.

## Файлы

| Файл | Назначение |
|---|---|
| `gitconfig-1c-erp.ini` | Основной профиль: настройки и 51 алиас |
| `gitconfig-modern-2.56.example.ini` | Подключаемый профиль упаковки, fetch и обслуживания для Git 2.56+ |
| `gitconfig-delta.example.ini` | Необязательный просмотр diff через установленный delta |
| `gitattributes-diff-only.example` | Дополнения для заголовков процедур BSL; не меняют окончания строк |
| `README_RU.md` | Установка, выбор параметров, примеры и откат |

Файл с расширением .ini уже имеет правильный синтаксис Git. Его можно подключить из .gitconfig или использовать как основу самого .gitconfig, сохранив свои user.name, user.email, credential, signing, proxy, include и настройки инструментов. Рекомендуется подключение.

## 1. Подключение

Сначала сделайте копию своего существующего .gitconfig. Поместите основной файл в домашний каталог Git под именем `gitconfig-1c-erp.ini`.

В каталоге ERP проверьте версию Git и пригодность файловой системы для untracked cache:

```console
git --version
git -c feature.manyFiles=false -c core.untrackedCache=false update-index --test-untracked-cache
```

Если тест завершился ошибкой, до подключения профиля отключите кеш для этого репозитория:

```console
git config --local core.untrackedCache false
```

Если тест прошёл, кеш включит feature.manyFiles. Проверьте так каждый репозиторий на другой файловой системе. Уже заданные локальные значения имеют приоритет над глобальным профилем.

Подключить профиль для всех репозиториев пользователя, один раз:

```console
git config --global --add include.path "~/gitconfig-1c-erp.ini"
```

Или подключить только для каталога с проектами 1С. Для этого вместо предыдущей команды добавьте в конец существующего .gitconfig один подходящий блок и замените путь:

Windows:

```gitconfig
[includeIf "gitdir/i:C:/src/1c/"]
    path = ~/gitconfig-1c-erp.ini
```

Linux/macOS:

```gitconfig
[includeIf "gitdir:~/src/1c/"]
    path = ~/gitconfig-1c-erp.ini
```

Завершающий / в условии нужен для репозиториев внутри каталога. Вариант gitdir/i сопоставляет путь без учёта регистра.

Проверить применение в каталоге ERP:

```console
git config --show-origin --get diff.algorithm
git config --show-origin --get feature.manyFiles
git var GIT_AUTHOR_IDENT
git s
```

Если имя и почта ещё не настроены, задайте собственные значения. user.useConfigOnly намеренно запрещает Git угадывать автора по имени учётной записи.

Для существующего репозитория формат индекса можно переключить отдельно:

```console
git update-index --index-version=4
```

Само index.version задаёт формат создаваемого индекса и не гарантирует преобразование уже существующего.

## 2. Почему выбраны эти настройки

| Настройка | Практический смысл |
|---|---|
| feature.manyFiles | Сжатие путей в индексе v4 и кеш поиска новых файлов |
| index.skipHash=false | Сохраняет контрольную сумму индекса; отменяет эту часть manyFiles для смешанного набора инструментов |
| fetch.writeCommitGraph | Поддерживает вспомогательную структуру для обхода истории |
| diff.algorithm=histogram | Кандидат на более понятный diff повторяющихся блоков; сравнивайте с Myers на своих изменениях |
| core.whitespace с cr-at-eol | Проверка пробелов принимает CRLF и продолжает находить настоящие хвостовые пробелы |
| merge.conflictStyle=zdiff3 | В конфликте видны обе стороны и общая база |
| rerere.enabled + autoupdate=false | Git вспоминает разрешение похожего текстового конфликта; добавление результата в индекс остаётся явным |
| pull.ff=only | При расхождении веток обычный pull останавливается и требует выбора merge или rebase |
| push.default=simple | Обычный push ориентирован на одноимённую ветку |
| push.autoSetupRemote=true | Первая обычная отправка ветки настраивает upstream; удобно для центрального GitLab |
| fetch.prune=true | Убирает устаревшие remote-tracking ветки; pruneTags=false не включает отдельное удаление тегов |
| rebase.autoSquash | Поддерживает fixup-коммиты в интерактивном rebase |

В fork-workflow с разными remote для чтения и отправки настройте remote.pushDefault и upstream отдельно; autoSetupRemote можно отключить локально. Настройки существующих branch.*, remote.* и параметры конкретной команды также влияют на поведение.

Histogram — выбор для просмотра. Он не превращает текстовое слияние XML в семантическое слияние метаданных 1С.

## 3. BSL: показывать процедуру или функцию в заголовке diff

Добавьте эти строки к существующему .gitattributes репозитория:

```gitattributes
*.bsl diff=bsl
*.os  diff=bsl
```

Для личной настройки без изменения командного файла можно добавить те же строки в `.git/info/attributes` основного репозитория.

Профиль определяет diff.bsl.xfuncname. Он учитывает русский и английский синтаксис, регистр букв, Асинх/Async и BOM перед первым объявлением. Ожидается UTF-8. Это регулярное выражение для навигации по diff, не парсер BSL.

Проверка на реально изменённом модуле:

```console
git dcode
git diff --function-context -- "src/ОбщиеМодули/МойМодуль/Ext/Module.bsl"
```

Если изменение находится прямо у начала процедуры, её объявление может оказаться в самом блоке diff, а не в заголовке.

Пользовательский diff-драйвер не передаётся автоматически другим разработчикам через Git и не настраивает отображение на сервере GitLab. Коллегам нужен этот профиль или аналогичное определение.

## 4. Окончания строк и кодировка

Основной профиль сохраняет существующие core.autocrlf, core.eol и правила .gitattributes. Он не выбирает за команду LF, CRLF или новую кодировку. Посмотреть состояние:

```console
git eol
git check-attr text eol working-tree-encoding -- "src/ОбщиеМодули/МойМодуль/Ext/Module.bsl"
```

Правила нормализации должны храниться в командном .gitattributes. Например, если команда выбирает LF внутри Git и CRLF в рабочей выгрузке:

```gitattributes
*.bsl text eol=crlf diff=bsl
*.os  text eol=crlf diff=bsl
*.xml text eol=crlf
*.mdo text eol=crlf
```

Это пример отдельного решения, не готовая миграция существующей ERP. Для LF в рабочем каталоге выбирают eol=lf. BOM и UTF-8 — отдельные свойства: eol не удаляет BOM и не перекодирует файл.

Не запускайте git add --renormalize . вместе с функциональными изменениями. Если нормализация нужна, выполняйте её в чистой отдельной ветке, оцените масштаб diff и проверьте загрузку/выгрузку используемыми инструментами 1С.

Не назначайте working-tree-encoding=UTF-16/CP1251 без проверки фактических байтов и всех клиентов. Не включайте merge=union для метаданных.

## 5. Ускорение рабочего каталога: ОС и диск

### FSMonitor

Для локального рабочего каталога в Windows/macOS со свежим native Git:

```console
git fsmonitor--daemon start
git config --local core.fsmonitor true
git fsmonitor--daemon status
```

В Linux встроенный демон реализован с Git 2.55. Проверьте поддержку конкретной сборки той же командой start; старому Linux Git не следует назначать fsmonitor=true как универсальное ускорение.

Если запуск не поддерживается, оставьте core.fsmonitor выключенным. Для отключения уже включённого монитора:

```console
git config --local core.fsmonitor false
git fsmonitor--daemon stop
```

Не переносите этот параметр автоматически на SMB/NFS/общие папки или на одну рабочую копию, которую открывают разные Git через WSL и Windows. Отдельные локальные рабочие копии проще проверять.

### Длинные пути в Windows

В существующем репозитории:

```console
git config --local core.longpaths true
```

При новом клонировании параметр можно передать сразу: `git -c core.longpaths=true clone <URL> <каталог>`. Он расширяет возможности самого Git, но не снимает ограничения всех редакторов, архиваторов и инструментов 1С. Короткий корневой путь вроде C:/src/erp также полезен.

### Параллельное извлечение файлов на SSD/NVMe

Начните с сравнения одного и четырёх процессов на копии репозитория:

```console
git config --local checkout.workers 4
```

Значение 0 означает все доступные логические ядра; оно не обязано быть лучшим. На HDD последовательный режим может оказаться быстрее. Возврат к нему:

```console
git config --local checkout.workers 1
```

Не ускоряйте status через core.ignoreStat, core.trustCtime=false или массовый assume-unchanged: у выгрузки ERP важно замечать изменения.

## 6. Обслуживание и новый профиль Git 2.56+

Для постоянной рабочей копии обслуживание включается отдельно в каждом нужном репозитории:

```console
git maintenance start
```

Команда регистрирует репозиторий и системное расписание. Базовый incremental-подход доступен более старым версиям. Не включайте это автоматически для временных каталогов Jenkins/Runner.

Если все инструменты этой рабочей копии используют Git 2.56+, можно испытать modern-профиль. Распакуйте комплект в `~/git-1c-erp-kit/` и подключите его локально:

```console
git config --local --add include.path "~/git-1c-erp-kit/gitconfig-modern-2.56.example.ini"
git maintenance start
```

Что включает профиль:

- pack.usePathWalk: группировка объектов по пути перед дополнительным поиском дельт. Для дерева с множеством Module.bsl это обоснованный кандидат на измерение.
- fetch.negotiationAlgorithm=skipping: другой обмен информацией об истории; меньше раундов не всегда означает меньше переданных данных.
- index.skipHash=true: пропуск контрольной суммы именно индекса. Хеши объектов не отключаются. Требуется совместимость всех native и встроенных Git-клиентов.
- maintenance.strategy=geometric: актуальная стратегия для больших репозиториев; может освобождать недостижимые данные по действующим срокам хранения.

Сам профиль не создаёт расписание. Команда maintenance start создаёт. Если в .git/config дальше уже заданы конфликтующие параметры, проверьте фактический результат через git config --show-origin --get maintenance.strategy.

Не запускайте одновременно ручной git gc и обслуживание. Не ставьте gc.auto=0 глобально без работающего замещающего обслуживания. Не используйте gc --aggressive как ежедневную кнопку.

Для первого построения фильтров изменённых путей, полезных для истории отдельных файлов, возможен отдельный запуск:

```console
git commit-graph write --reachable --changed-paths
```

Первый запуск в большой истории может занять время; не добавляйте его в каждый коммит.

### Как измерять

На отдельной копии выполните прогрев, затем по 5 одинаковых запусков до и после и сравните медиану:

- git status --short --branch: неизменённая копия и копия после типовой выгрузки;
- git diff --stat: небольшой фикс и обновление ERP;
- переключение между двумя репрезентативными ветками в чистом каталоге;
- fetch/push с одинаковыми исходными объектами, если сравниваете упаковку;
- длительность обслуживания, размер .git, пик RAM.

Пример для PowerShell, показывает один замер:

```powershell
(Measure-Command { git status --short --branch | Out-Null }).TotalMilliseconds
```

Последовательные fetch одной ветки без новых объектов не сравнивают скорость загрузки обновления. Не ожидайте фиксированного процента ускорения без замеров на вашей ERP.

Для проверки задачи после обновления ссылок:

```console
git fa
git dstat origin/develop...HEAD
git dcode origin/develop...HEAD
git check-staged
git s
```

Три точки показывают изменения от общей базы; две ревизии без трёх точек сравнивают два конкретных снимка. Для полного сравнения релизов обычно нужны именно два снимка: `git dquick TAG1 TAG2`.

Worktree экономит повторное клонирование базы объектов и позволяет держать ERP, релиз и хотфикс в отдельных каталогах. Файлы рабочих каталогов при этом занимают место отдельно.

## 8. Необязательный delta

Профиль не требует delta. Если хотите просмотр diff с номерами строк и переходами между файлами, сначала установите его и проверьте:

```console
delta --version
```

Затем подключите локально или глобально файл `gitconfig-delta.example.ini` из распакованного комплекта. Например, только для текущего репозитория:

```console
git config --local --add include.path "~/git-1c-erp-kit/gitconfig-delta.example.ini"
```

Для обхода pager на один раз: `git --no-pager diff`. Delta оформляет текстовый diff; это не семантический анализатор 1С.

## 9. Что важно вне .gitconfig

Исходники конфигурации и результаты сборки имеют разный жизненный цикл. Большие DT/CF/CFU и архивы обычно удобнее хранить как артефакты сборки. Если бинарный файл действительно должен версионироваться, команда выбирает Git/LFS и серверную поддержку явно; пример .gitattributes ничего не переводит в LFS.

Не ставьте глобально diff.renameLimit=0 или огромные лимиты. Для массового сравнения есть dquick; для обычного diff и merge распознавание переименований сохранено.

Не включены: http.postBuffer в гигабайтах, отключение TLS, safe.directory=*, выключение проверок изменений, автоматический force push, безусловный autostash, глобальный filemode=false/ignoreCase=false, experimental-пакет целиком. Каждому из этих решений нужен отдельный контекст.

Sparse checkout / sparse index и partial clone оставлены за пределами профиля: загрузке полной конфигурации 1С может понадобиться всё дерево, а сервер и IDE должны поддерживать выбранный режим. Для изолированного ревью возможна отдельная неполная рабочая копия после проверки инструментов. Reftable также требует отдельной проверки всех клиентов.

После разрешения конфликтов BSL/XML нужны проверка загрузки/сборки конфигурации и тесты. Чистый текстовый merge и повторное решение rerere не доказывают корректность метаданных ERP.

Настройки рабочего клиента не меняют конфигурацию сервера GitLab. CI должен получать только параметры, необходимые его операциям, а не целиком пользовательский профиль с pager, редакторами и личными алиасами.

## 10. Откат

Для глобального подключения из шага 1:

```console
git config --global --fixed-value --unset-all include.path "~/gitconfig-1c-erp.ini"
```

Для includeIf удалите только добавленный блок. Локальный modern-профиль:

```console
git config --local --fixed-value --unset-all include.path "~/git-1c-erp-kit/gitconfig-modern-2.56.example.ini"
```

Локальный delta-профиль отключается аналогично по его точному include.path. Если меняли отдельные local-параметры, восстановите прежние значения.

Убрать текущий репозиторий из фонового обслуживания: `git maintenance unregister`. Команда `git maintenance stop` останавливает общее расписание пользователя и может затронуть другие зарегистрированные репозитории. После unregister проверьте изменения maintenance.auto/gc.auto и восстановите исходные значения при необходимости.

## 11. Что проверено

Автоматическая функциональная проверка: native Git 2.51.1, Linux, локали C и C.UTF-8, изолированные временные репозитории.

- Все три INI-файла разобраны парсером Git.
- Все 51 алиас выполнены на подходящих сценариях; для add --patch ответы поданы через stdin.
- 26 проверок поведения: фильтры BSL/XML, кириллические пути, BOM/CRLF, заголовки процедур, staging, stash, worktree, fixup/autosquash, реальный конфликт zdiff3, повторное решение rerere и отсутствие автодобавления в индекс, отказ ff-only при расхождении.
- В тестовой файловой системе тест untracked cache не прошёл; проверена работа с локальным core.untrackedCache=false. Поддержка кеша на вашем диске требует собственного теста.

Не проверялись исполнение на Windows/macOS, внешний delta и выполнение modern-профиля на Git 2.56. Проверка синтаксиса не подтверждает поддержку каждого нового параметра старой версией Git. Скорость на реальной ERP не измерялась.
